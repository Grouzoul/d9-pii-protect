Extension Directus / d9 · anonymisation gouvernée

Vos agents IA lisent vos données.
Jamais vos données personnelles.

Écluse est un plugin d9 qui détecte les PII françaises dans vos champs texte libre et les chiffre à la volée, de façon réversible, pour tout agent IA — sans toucher à ce que voient vos utilisateurs humains.

Démarrage rapide Comment ça marche

Pitch

d9 sait qui a le droit d'accéder à quoi. Il ne sait pas qu'un numéro de sécurité sociale traîne dans un champ commentaire.

Le RBAC de d9 protège des champs entiers (par rôle, par ligne). Mais une PII cachée dans un champ texte libre autorisé — un NIR dans une note, un nom dans un message de ticket — passe en clair dans le contexte de l'agent. Une fois dans le contexte, elle part au modèle : egress, rétention, hors de votre contrôle.

Écluse ferme ce trou. Pour un utilisateur de rôle « agent », le plugin intercepte la lecture, détecte les PII dans le contenu, et les remplace par un chiffré réversible. L'agent raisonne sur la donnée, agit, réécrit — sans jamais voir la moindre information personnelle. Un humain autorisé, porteur de la clé, ré-identifie sous audit.

PositionnementDeux briques complémentaires : d9 expose et gouverne l'accès (API, rôles, tokens) ; Écluse anonymise le contenu, quelle que soit la source. FR-first, déployé dans votre environnement.

Comment ça marche

Écluse est un hook Directus (non-sandboxé) branché sur le cycle de vie des items. Il appelle un moteur d'anonymisation local qui détecte les PII (modèle FR) et les chiffre in-place.

→

À la lecture — anonymisation

Si le demandeur a un rôle agent, chaque champ texte libre configuré traverse l'engine. Les PII deviennent des marqueurs auto-porteurs [[ECLUSE:TYPE:chiffré]] : l'agent voit le type (pour raisonner) mais jamais la valeur.

// réponse vue par un agent
{ "note": "Le client [[ECLUSE:PERSON:9MUXB2me…]] (NIR [[ECLUSE:FR_NIR:C1OIENV…]])
            conteste un prélèvement sur son IBAN [[ECLUSE:IBAN_CODE:mpoZ9GG…]]." }

// même enregistrement, vu par un humain (rôle admin)
{ "note": "Le client Jean Dupont (NIR 1 85 05 78 006 084 36)
            conteste un prélèvement sur son IBAN FR7630006000011234567890189." }

À l'écriture — rehydratation

Quand un agent réécrit un enregistrement en renvoyant des marqueurs (il a modifié le statut, ajouté une note…), le hook les déchiffre avant persistance. La vraie donnée est restaurée en base, intacte. L'agent n'a jamais eu besoin de voir le clair pour travailler dessus.

Round-trip prouvéAgent lit (chiffré) → modifie → réécrit → la base contient la PII d'origine, zéro corruption. « Rehydrate » = terme générique de l'opération inverse ; Écluse n'embarque aucun SDK tiers.

Démarrage rapide

  1. Posez l'extension dans le dossier extensions/ de votre d9 (hook non-sandboxé — accès à l'accountability). 
    extensions/
└─ directus-extension-ecluse/
   ├─ package.json   # "directus:extension": { type:hook, path+source }
   └─ index.js
  2. Lancez le moteur d'anonymisation (détection FR + chiffrement), joignable par d9. 
    ECLUSE_ANALYZER_URL=http://presidio-fr:5005/analyze \
ECLUSE_KEY=<clé AES 32o>  python ecluse_engine.py   # :8077
  3. Déclarez vos rôles agents et champs dans ecluse.config.json (lu à chaud).
  4. C'est tout. Un agent lit l'API d9 habituelle : les PII des champs ciblés sont chiffrées. Un humain voit le clair. 
    curl /items/tickets -H "Authorization: Bearer $TOKEN_AGENT"
# → note : "… [[ECLUSE:FR_NIR:…]] …"
Déployé chez vousd9, Écluse et le moteur FR tournent dans votre environnement. Aucune PII en clair ne sort vers un tiers.

Configuration

Un seul fichier, relu à chaud (pas de redémarrage) : extensions/ecluse.config.json.

{
  "engine": "http://host.docker.internal:8077",
  "agentRoleIds": ["afd7a516-01a7-4ac0-9046-e1953ce811d8"],
  "fields": { "tickets": ["note"] }
}
CléRôle
engineURL du moteur d'anonymisation (dans votre réseau).
agentRoleIdsRôles d9 traités comme « agents » → anonymisation activée. Les autres rôles voient le clair.
fieldsCollections → champs texte libre à passer dans le moteur.

Modèle de sécurité

  • AES-256-GCM, nonce aléatoire par valeur. Impossible à reconstituer sans la clé — y compris pour une PII à faible entropie (NIR, téléphone), que les approches par hash non salé laissent brute-forcer.
  • Zéro fuite d'égalité. La même valeur donne deux chiffrés différents : un agent ne peut même pas déduire que deux fiches partagent le même NIR.
  • Réversibilité gouvernée. Le chiffré est déchiffrable par le porteur de clé — pas par l'agent, qui ne voit jamais la clé. C'est de la pseudonymisation contrôlée (ré-identification sous RBAC + audit), pas du masquage à sens unique.
  • Fail-closed. Si le moteur est indisponible, le champ est masqué ([protégé — Écluse indisponible]), jamais laissé en clair. Une panne ne provoque pas de fuite.
  • Authentifié (GCM). Toute altération d'un chiffré est détectée.
Où va le risqueLa sécurité repose désormais sur la custody de la clé, pas sur la difficulté de cassage. En production : clé en KMS/HSM, rotation, accès RBAC + journal des ré-identifications. (POC : clé de démo en dur.)

Moteur de détection FR

Là où les outils du marché (hoop, Presidio par défaut, vaults SaaS) sont anglophones, Écluse est FR-first : NER français (CamemBERT / Anonym-IA) pour les noms, lieux et le NIR, plus des recognizers structurés (IBAN, téléphone, email) et des customs SIREN / SIRET (Luhn) et dates textuelles françaises.

Rappel mesuré sur un corpus FR identique (46 PII), même règle de comptage :

MoteurRappelIDs FR (NIR/SIREN/SIRET)
hoop · Alcatraz (défaut)0,350 / 8
hoop · Presidio (EN)0,87≈ 0 réel
Écluse (FR-first)1,008 / 8

Détection servie par Microsoft Presidio + modèles FR open source ; le moteur est interchangeable (on choisit le NER).

Roadmap

Le POC couvre déjà le cœur : détection FR, chiffrement réversible, round-trip, fail-closed. Évolutions simples à venir :

  • Custody de clé — KMS/HSM, rotation, et journal d'audit des ré-identifications (qui a déchiffré quoi, quand).
  • Policies par champ en UI — choisir par champ l'opérateur (chiffrer / hash-à-clé / rédiger) depuis le studio d9, au lieu du fichier config.
  • Recognizers FR additionnels — RIB, plaque, n° de dossier, cadastre ; NER custom branchable (CamemBERT / Anonym-IA en ONNX).
  • Mode « API existante » — la même brique d'anonymisation en ligne devant une API tierce (Airtable, service interne), hors d9.
  • Chiffrement déterministe optionnel — préserver les clés de jointure quand c'est requis (protégé par la clé, contrairement au hash).
