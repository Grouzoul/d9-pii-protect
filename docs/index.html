Extension d9 · anonymisation gouvernée

Vos agents IA lisent vos données.
Jamais vos données personnelles.

Une extension d9 qui détecte les PII françaises dans vos champs texte libre et les chiffre à la volée, de façon réversible, pour tout agent IA — sans toucher à ce que voient vos utilisateurs humains.

Démarrage rapide → Comment ça marche

Pitch

d9 sait qui a le droit d'accéder à quoi. Il ne sait pas qu'un numéro de sécurité sociale traîne dans un champ commentaire.

Le RBAC de d9 protège des champs entiers (par rôle, par ligne). Mais une PII cachée dans un champ texte libre autorisé — un NIR dans une note, un nom dans un message de ticket — passe en clair dans le contexte de l'agent. Une fois dans le contexte, elle part au modèle : egress, rétention, hors de votre contrôle.

L'extension ferme ce trou. Pour un utilisateur de rôle « agent », elle intercepte la lecture, détecte les PII dans le contenu, et les remplace par un chiffré réversible. L'agent raisonne sur la donnée, agit, réécrit — sans jamais voir la moindre information personnelle. Un humain autorisé, porteur de la clé, ré-identifie sous audit.

Comment ça marche

Un hook d9 (non-sandboxé) branché sur le cycle de vie des items. Il appelle un moteur d'anonymisation local qui détecte les PII (modèle FR) et les chiffre in-place.

À la lecture — anonymisation

Si le demandeur a un rôle agent, chaque champ texte libre configuré traverse le moteur. Les PII deviennent des marqueurs auto-porteurs [[PII:TYPE:chiffré]] : l'agent voit le type (pour raisonner) mais jamais la valeur.

// réponse vue par un agent
{ "note": "Le client [[PII:PERSON:9MUXB2me…]] (NIR [[PII:FR_NIR:C1OIENV…]])
            conteste un prélèvement sur son IBAN [[PII:IBAN_CODE:mpoZ9GG…]]." }

// même enregistrement, vu par un humain (rôle admin)
{ "note": "Le client Jean Dupont (NIR 1 85 05 78 006 084 36)
            conteste un prélèvement sur son IBAN FR7630006000011234567890189." }

À l'écriture — rehydratation

Quand un agent réécrit un enregistrement en renvoyant des marqueurs (il a modifié le statut, ajouté une note…), le hook les déchiffre avant persistance. La vraie donnée est restaurée en base, intacte. L'agent n'a jamais eu besoin de voir le clair pour travailler dessus.

Round-tripAgent lit (chiffré) → modifie → réécrit → la base contient la PII d'origine, zéro corruption.

Fichiers (documents texte)

Un document .txt / .docx téléchargé par un agent (/assets) est tokenisé réversiblement ; s'il le ré-uploade (nouvelle version), les marqueurs sont rehydratés avant stockage. L'agent peut donc lire ET mettre à jour un document sans jamais voir la PII ; un humain récupère toujours l'original. (Images & PDF scannés : caviardage destructif — roadmap.)

Démarrage rapide

  1. Posez l'extension dans le dossier extensions/ de votre d9 (hook non-sandboxé — accès à l'accountability). 
    extensions/
└─ directus-extension-ecluse/
   ├─ package.json   # "directus:extension": { type:hook, path+source }
   └─ index.js
  2. Lancez le moteur d'anonymisation (détection FR + chiffrement), joignable par d9. 
    PII_ANALYZER_URL=http://presidio-fr:5005/analyze \
PII_PROTECT_KEY=<clé AES 32o>  python engine.py   # :8077
  3. Marquez le rôle « Agent IA » (toggle is_agent sur le rôle) et déclarez les champs à protéger dans ecluse.config.json (lu à chaud).
  4. C'est tout. Un agent lit l'API d9 habituelle : les PII des champs ciblés sont chiffrées. Un humain voit le clair. 
    curl /items/tickets -H "Authorization: Bearer $TOKEN_AGENT"
# → note : "… [[PII:FR_NIR:…]] …"
Déployé chez vousd9, l'extension et le moteur FR tournent dans votre environnement. Aucune PII en clair ne sort vers un tiers.

Modèle de sécurité

  • AES-256-GCM, nonce aléatoire par valeur. Impossible à reconstituer sans la clé.
  • Zéro fuite d'égalité. La même valeur donne deux chiffrés différents : un agent ne peut même pas déduire que deux fiches partagent le même NIR.
  • Réversibilité gouvernée. Le chiffré est déchiffrable par le porteur de clé — pas par l'agent, qui ne voit jamais la clé. Pseudonymisation contrôlée (ré-identification sous RBAC + audit), pas du masquage à sens unique.
  • Fail-closed. Si le moteur est indisponible, le champ est masqué ([protégé — indisponible]), jamais laissé en clair. Une panne ne provoque pas de fuite.
  • Authentifié (GCM). Toute altération d'un chiffré est détectée.
Custody de cléKMS/HSM, rotation, journal d'audit des ré-identifications.

Moteur de détection FR

Là où les outils du marché (hoop, Presidio par défaut, vaults SaaS) sont anglophones, cette extension est FR-first : NER français (CamemBERT / Anonym-IA) pour les noms, lieux et le NIR, plus des recognizers structurés (IBAN, téléphone, email) et des customs SIREN / SIRET (Luhn) et dates textuelles françaises.

L'objection

« Un LLM self-hosté ou Bedrock, ça ne suffit pas ? »

Héberger le modèle soi-même, ou l'appeler via Bedrock (pas d'entraînement, résidence UE), sécurise un seul maillon : l'inférence. Ça ne répond ni à l'exigence RGPD de minimisation, ni à la traînée de l'agent.

Raison n°1 — RGPD pur : minimisation (art. 5.1.c)Avant même la technique : une donnée personnelle non nécessaire à la tâche ne doit pas être traitée — donc pas envoyée à une IA, où qu'elle tourne. Un agent support n'a pas besoin du NIR en clair pour traiter un ticket ; le lui transmettre viole la minimisation, même self-hosté, même en UE. (L'EDPB rappelle en 2025 qu'un modèle n'est « anonyme » que si l'extraction de PII y est « insignifiante » — la plupart échouent.)

Raison n°2 — la traînée. Et même la PII que tu envoies ne reste pas dans l'inférence : self-hosté / Bedrock = le où du hop modèle ; la tokenisation = le quoi l'agent voit, et elle couvre tous les endroits où sa donnée atterrit.

L'inférence = 1 hop. Un agent = N points de persistance.

Roadmap

Le POC couvre déjà le cœur : détection FR, chiffrement réversible, round-trip, fail-closed. Évolutions simples à venir :

  • Secure-by-default — chiffré par défaut, clair uniquement pour une allowlist de rôles humains (fail-safe).
  • Rotation de clés / fenêtre de validité — tokens liés à une version de clé horodatée : un document ré-uploadé hors fenêtre n'est plus rehydratable (clé tournée) → réversibilité bornée dans le temps.
  • Custody de clé — KMS/HSM, rotation, et journal d'audit des ré-identifications (qui a déchiffré quoi, quand).
  • Policies par champ en UI — choisir par champ l'opérateur (chiffrer / hash-à-clé / rédiger) depuis le studio d9, au lieu du fichier config.
  • Recognizers FR additionnels — RIB, plaque, n° de dossier, cadastre ; NER custom branchable (CamemBERT / Anonym-IA en ONNX).
  • Mode « API existante » — la même brique d'anonymisation en ligne devant une API tierce (Airtable, service interne), hors d9.
  • Caviardage images / PDF scannés — OCR destructif (Presidio image-redactor + OCR FR). Les documents texte (.txt/.docx) sont déjà tokenisés réversiblement, y compris au téléchargement via /assets.
  • Industrialisation release — tout en variables d'environnement (clé via KMS, sans valeur par défaut), config relative, secrets hors du compose.
  • Chiffrement déterministe optionnel — préserver les clés de jointure quand requis.
