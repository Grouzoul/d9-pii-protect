d9 extension · governed anonymization

Your AI agents read your data.
Never your personal data.

A d9 extension that detects French PII in your free-text fields, documents and images, and encrypts (or redacts) it on the fly, reversibly, for any AI agent — without touching what your human users see.

Quick start → Interactive comparator How it works

Pitch

d9 knows who is allowed to access what. It doesn't know that a social security number is sitting in a comment field.

d9's RBAC protects entire fields (by role, by row). But a PII hidden in an authorized free-text field — an NIR in a note, a name in a ticket message — flows through in the clear into the agent's context. Once in the context, it goes to the model: egress, retention, out of your control.

The extension closes this gap. For a user with an "agent" role, it intercepts the read, detects PII in the content, and replaces it with a reversible ciphertext. The agent reasons about the data, acts, rewrites — without ever seeing a single piece of personal information. An authorized human, holding the key, re-identifies under audit.

On read — anonymization

If the requester has an agent role, every free-text field passes through the engine — by default, with no configuration. PII becomes self-describing markers [[PII:TYPE:ciphertext]]: the agent sees the type (to reason about it) but never the value.

// response seen by an agent
{ "note": "Le client [[PII:PRENOM_PERSONNE:9MUXB2me…]] [[PII:NOM_PERSONNE:a7Fz…]]
            (NIR [[PII:NUM_SECURITE_SOCIALE:C1OIENV…]]) conteste un prélèvement
            sur son IBAN [[PII:IBAN_CODE:mpoZ9GG…]]." }

// same record, seen by a human (admin role)
{ "note": "Le client Jean Dupont (NIR 1 85 05 78 006 084 36)
            conteste un prélèvement sur son IBAN FR7630006000011234567890189." }

On write — rehydration

When an agent rewrites a record by sending back markers (it changed the status, added a note…), the hook decrypts them before persistence. The real data is restored in the database, intact. The agent never needed to see the clear text to work on it.

Round-tripAgent reads (encrypted) → edits → rewrites → the database holds the original PII, zero corruption.

Files — secure-by-default on everything

Not just fields: any file accessible to an agent is protected on the fly at download (/assets), depending on its type:

  • Text documents (.txt / .md / .csv / .json / .docx) → reversibly tokenized, like fields. If it re-uploads them, the markers are rehydrated before storage: the agent can read AND update without ever seeing the PII.
  • Images (PNG/JPG…) → redacted (OCR + masking of PII zones). Destructive for the agent's copy; the stored file stays intact and the authorized human downloads the original.
  • Unsupported type (PDF, binary…) → fail-closed refusal (HTTP 415). Nothing is allowed to leak by default.

Quick start

  1. Launch the reference stack (d9 + the sidecar engine). The engine builds itself. 
    cd deploy
cp .env.example .env            # set PII_PROTECT_KEY
docker compose up -d --build    # d9 on :8055 + engine
  2. Mark the "AI Agent" role: enable the is_agent toggle on the role definition (that's the only interface addition).
  3. That's it — secure-by-default. With no config at all, every text field and every file accessible to this role is protected. An agent reads the usual d9 API; a human sees the clear text. 
    curl /items/tickets -H "Authorization: Bearer $TOKEN_AGENT"
# → note: "… [[PII:NUM_SECURITE_SOCIALE:…]] …"
Deployed on your sided9, the extension and the FR engine run in your environment — one engine per environment. No PII in the clear ever leaves to a third party.

Configuration

Everything is driven by environment variables — no config file, no coupling to a specific environment. By default everything is protected; you restrict afterward.

VariableBuilding blockRole
PII_PROTECT_KEYengineAES-256 key (secret/KMS in prod). Custody = the security boundary.
PII_PROTECT_ENGINE_URLextensionURL of the sidecar engine (within the environment's network).
PII_PROTECT_FIELDSextensionJSON {collection:[fields]} to restrict. Empty = all text fields.
PII_PROTECT_ENTITIES / PII_PROTECT_SKIPengineAllow-list / deny-list of PII types to encrypt.
PII_NER_MODELengineHuggingFace NER model (language/model swap — see engine/MODELS.md).
Toggle is_agentroleDesignates "agent" roles on the role page. Others see the clear text.

Security model

  • AES-256-GCM, random nonce per value. Impossible to reconstruct without the key.
  • Zero equality leakage. The same value yields two different ciphertexts: an agent cannot even infer that two records share the same NIR.
  • Governed reversibility. The ciphertext is decryptable by the key holder — not by the agent, which never sees the key. Controlled pseudonymization (re-identification under RBAC + audit), not one-way masking.
  • Fail-closed. If the engine is unavailable, the field is masked ([protected — unavailable]), never left in the clear. An outage does not cause a leak.
  • Authenticated (GCM). Any tampering with a ciphertext is detected.
Key custodyKMS/HSM, rotation, audit log of re-identifications.

FR detection engine

Where market tools (hoop, Presidio by default, SaaS vaults) are English-speaking, this extension is FR-first: French NER (CamemBERT / Anonym-IA) for names, places and the NIR, plus structured recognizers (IBAN, phone, email) and custom SIREN / SIRET (Luhn) and French textual dates.

Concept

Why hosting the model is not enough

Running the model on your own infrastructure, or via a provider like Bedrock (no training, in an EU region), secures where inference happens. That's useful, but two problems remain untouched — and neither depends on where the model runs.

1. Data minimization

The GDPR (article 5.1.c) requires processing only the personal data necessary for the task. A support agent does not need to read a social security number in the clear to handle a ticket. Passing it along — even to an internally hosted model — is still one processing step too many. The question is not "where to send the data", but "whether to send it".

2. Propagation through the agent's chain

The data an agent receives does not stay within the model call: it is logged and stored all along the chain.

  • Traces and observability — tracking tools record inputs and outputs, often by default, sometimes on a third-party service.
  • Tool results — what an agent reads from the database comes back into its context, then into the logs.
  • Memory and conversation history.
  • Caches and application logs.
  • Downstream systems the agent feeds.

Each step is a copy of the data, to secure, audit and retain. Hosting the model covers only one of them.

The answer: protect the content, at the source

By detecting and encrypting personal data before it enters the agent's context, you address both problems at once: what is unnecessary is never transmitted, and what circulates afterward — traces, memory, logs — is already encrypted. Only one place remains where the data is in the clear: the source.

Key takeawayHosting (self-hosted / Bedrock) decides where the data is processed. Content protection decides which data is exposed. The latter is the GDPR's minimization requirement — hosting does not replace it.

Roadmap

Already shipped: FR detection (Presidio + Anonym-IA), reversible AES-GCM encryption, read/write round-trip, secure-by-default on all text fields, documents and images (OCR redaction), fail-closed refusal of unsupported types, everything driven by environment variables.

Coming soon:

  • Human validation (HITL) — hold + approval link for re-identification; email notifications then Slack / Teams / 2FA. Phase 2, possibly paid.
  • Key rotation / validity window — tokens tied to a timestamped key version → time-bounded reversibility; custody via KMS/HSM + audit log of re-identifications.
  • PDF (text and scanned) — today refused fail-closed, for lack of a PDF OCR pipeline.
  • Optional deterministic mode — same input → same token, to preserve join keys when required.
  • 1-click distribution — extension published on npm (Directus marketplace) + engine on a container registry (GHCR).
  • Standalone sidecar — the same anonymization block in front of a third-party API, outside d9.
  • Additional FR recognizers + per-language NER tuning (quantized ONNX NER to lighten the image).
